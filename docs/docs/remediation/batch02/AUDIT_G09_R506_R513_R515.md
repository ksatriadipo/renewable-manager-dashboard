### r506: PASS_WITH_CONDITIONS

**Root cause, g09a.** The cause is the synchronous `AddDirectorXp` → `DirectorLeveledUp` → `QueuePopup`, which shows immediately while no modal is open. It is confirmed in code.

The fix, in `HubHUD.Missions.cs:CheckMission`, changes the ON order to: queue "Misi selesai", then XP, then OnMissionStarted + SaveAll.
- "Misi selesai" opens at once and "Naik level!" queues behind it, so the cause now appears before the effect.
- `_profile.mission++` still runs before both, so `MissionTitle()` inside the popup body is unchanged.
- `OnMissionStarted` only calls `Tip(MissionTip(next))`. It now queues because the modal is open. It does not open or close a modal (checked), so it cannot destroy the mission modal.
- The relative order XP → OnMissionStarted → SaveAll is kept, and the tests assert it.

**Root cause, g09b.** `Toast` was written into the old Tasks `_modalToast`, which `OpenTasks` → `CloseModal` then destroyed. The new ON order is save → reopen → toast, so the toast lands in the new modal. A level-up during the claim queues behind the open Tasks modal, so nothing is lost.

**Switch:** OFF is byte-for-byte the old order for both items (`PopupOrderG09.MissionFirst` and `PopupOrderG09.ClaimToastAfter`).

**Flow regressions:**
- F6d `QaMission1DoneStep` still works: it now reaches `StepMissionDone` directly, with `levelup_closed_before = 0` instead of 1.
- No classifier in `tools/` reads that metric (grep).
- The doc comment of `UiDevQa.MissionDoneStep` (`UiDevQa.cs:328–331`) still describes the old order as product behaviour. It is documentation only, but now wrong.

**Tests vs revert:**
- Reverting the order inside `PopupOrderG09` fails `G09a_On_*` and `G09b_On_*`.
- Reverting the **HubHUD wiring** (calling the old sequence directly) fails no test, because the tests model a HUD instead of exercising `HubHUD` (see C-G09-01).

**Per-frame cost:** none. The change is event-driven only.

### r513: PASS_WITH_CONDITIONS

**Root cause.** Two texts were shown for one event: the short `.hud` variant was registered for `ToastHudFit` in the top lane, while the full text went to `_modalToast` and the bottom lane.

**Fix.** ON uses `quest.done.toast.hud` with the full name everywhere and registers no variant, so `ToastHudFit` returns null and the text stays identical in every lane and in the modal.
- The `.hud` key exists in all 7 languages with `{0}` (`strings.csv:2264`), so the claim hint "· klaim di Tugas" is kept.
- ToastHudVariant has no other caller, so no other toast changes.

**Switch:** OFF is the old code exactly.

**Residual risk.** A long quest name is no longer shortened. When the top lane does not fit it on one line, the toast drops to the bottom lane or the page ribbon instead. The text stays whole, with no ellipsis, but placement over cards or buttons is unmeasured (C-G09-04).

**Tests vs revert:**

- Its lane model (`Fits`, 11 px per character) is a heuristic, not `ToastBoxHeight`.
- A revert of the `HubHUD.Quests` wiring alone is not caught (C-G09-01).

**Per-frame cost:** none.

### r515: PASS_WITH_CONDITIONS

**Root cause (RC-U1-08).** The queue stored rendered strings with no validity check, and P3/P4 re-copied every shown toast on each modal or slot-picker open.

**Fix.** `_mailQueue` becomes `GuidanceQueue` entries `{Text, Valid, BornAt, MaxAge, NoCopy}`.
- `TryDequeue` re-evaluates the predicate and age against the current state and drops stale entries.
- `CopyShownToast` (`OpenModal` + `OpenSlotPicker`) copies only toasts shown for less than 1 s, carrying their original predicate, and never NoCopy toasts.

Predicates:
- `sp.started`: `!j.Done`. `j` is the started `SmallJob` and `Done` is a real field (`SmallProjects.cs:210+`).
- `quest.done`: `Quests.State(id).Status == Done`, which also covers U1-029 replay after a claim.
- `quest.claimed`: maximum age 3 s plus NoCopy.
- World events (QuestMech, WorldAlive, WorldAliveMap): maximum age 30 s, measured in `unscaledTime`.
- Tender mail and HQ tier body: legacy entries, always valid with no age limit, so the G01 gate is untouched.

This matches RCA R-G09-1 one-to-one.

**Switch:** OFF is equivalent to the old code, checked branch by branch:
- `IsLive` is always true, so `TryDequeue` behaves as FIFO.
- `ShouldCopyOnInterrupt` is always true and copies `_toast.text` as before.
- The `<1 s` re-queue branch uses the same `Contains` + `ToastQueueMax` checks.
- `PumpMail` uses the same `_nextMailToastAt` 2.6 s cadence.

**Interaction:**
- r506 g09b toast: it is shown inside the new modal, never queued, and NoCopy, so it is neither lost nor doubled.
- r506 g09a: toasts that arrive while "Misi selesai" is open queue with their predicates.
- r513: no variant is registered, so `_toast.text` equals `Entry.Text` when copied.

**Residual edges:**
- (a) `_toastMeta` and `_toastShownAt` are shared by the HUD toast and `_modalToast`. In a narrow same-frame case (a modal toast shown while the HUD `resolvedStyle` still reports Flex), the HUD text can be copied with the modal toast's metadata. OFF would always copy anyway, so this is not a regression, but it is untested.
- (b) A toast that was visible for 1–2.5 s and then interrupted by a modal is not replayed. This includes tender mail. That is intended (treated as read), and the Mail badge remains, but it is a UX change that needs to be seen in captures 07 and 21.
- (c) Pre-existing, not caused by this patch: when `sp.started` is fired while a modal is open, it goes to `_modalToast`, and the very next `CloseModal` destroys it.
- (d) U1-012 holds only if the stale "Dimulai" in capture 11 was a replay. RCA rates that PROBABLE. If it was the still-visible original 2.5 s toast, r515 does not change it, because the currently shown toast is not re-validated.

**Tests vs revert:**
- `GuidanceQueueTests` fail if the predicate, age or copy logic reverts, and `SwitchOff_*` locks the legacy behaviour.
- The wiring (predicate on `sp.started`, `CopyShownToast` in OpenModal and Slots) is not covered (C-G09-01).
- `Dropped` and `LastDropped` exist, but no QA output logs them (C-G09-03).

**Per-frame cost:**
- `Update` calls `PumpMail` only under the old condition (queue non-empty and timer due).
- Predicates are O(1) or one quest lookup, evaluated at dequeue (at most once per 2.6 s).
- There is one struct plus closure allocation per toast event.
- Acceptable.

### r514: PASS_WITH_CONDITIONS

**Root cause.** The only tip invalidation was `StaleForLevel`. Event state (a new project started, mission advanced, queue age) was ignored.

**Fix.** `GuideTips.StaleFor(id, TipState)` keeps `StaleForLevel` first and, when ON, adds two rules:
- **Mission tips `m_*`:** stale when `MissionTip(CurrentMission.Key) != id`.
  - `CurrentMission` clamps to the last mission (`Missions.cs:100`).
  - With r506 the new mission's tip is queued after `_profile.mission++`, so it is current and not stale.
  - The finished mission's tip is now stale, which is the intended U1-014 effect.
- **`SmallPaid`:** stale when `SmallJobsDone > 1`, when a project was started after queueing (`done + running` increased), or when the queue age exceeds 60 s.
  - Age is measured in `realtimeSinceStartup`, the same clock as `Tip()`'s `now` (`Tips.cs:112`).

Two further mechanisms:
- **Visible tips:** `TipStale(_tipId)` already closes a shown tip (`Tips.cs:187`). `_tipQueuedAt` is kept until close, so a visible SmallPaid closes once it becomes stale. That addresses the "persists 45–49" half of U1-014, where the overlay timer was frozen by toasts.
- **Mid-run switch:** turning the switch ON while the game runs is safe, because missing entries give −1 and are not judged.

**Switch:** OFF is the old formula exactly, and `_tipQueuedAt` is not filled.

**Residuals:**
- A SmallPaid queued for about 59 s can be shown, and Fire marks it seen, then close about 1 s later. That is a short flash, and the tip never returns.
- Non-SmallPaid tips still persist through the frozen overlay timer (the `_tipOverlayUntil += dt` path is unchanged).

**Tests vs revert:**
- `GuideTipsStateStaleTests` fail if the `StaleFor` rules revert.
- `SwitchOff_EqualsStaleForLevel` locks OFF over a 12 tips × 8 levels table, and the old `StaleForLevel` cases are re-asserted.
- The `HubHUD.Tips` wiring is not covered (C-G09-01).

**Per-frame cost:**
- `TipStale` runs per queued tip plus the shown tip, in `TipPump` (from `Refresh`, every 0.5 s).
- `RunningSmallJobs.Count()` is a LINQ `Where` enumeration with a small allocation every 0.5 s.
- Acceptable. It is not per-frame, except in the QA-only `ViewShot` loop.
